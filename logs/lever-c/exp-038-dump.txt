Notes
-----

* The planned experiment said "normal boot of dbgC8". This run deviates on
  three condition points — the stock 7.2.6+192p kernel instead of the CI
  a699dd6 kernel, a plain Netac stick instead of the CI stick, cold-plug
  instead of pre-plug. None of them can confound the tuning comparison:
  the eight KEY registers are never written by the driver in either kernel
  (upstream phy-qcom-eusb2-repeater.c writes only fd46 + the init-table
  fd51/fd54/fd57 + DT overrides fd57/fd53/fd51 (+fd52/fd54 only if the
  board DT carried qcom,tune-res-fsdif / qcom,squelch-detector-bp — this
  board's repeater node has neither), set_mode writes fde8/fded outside
  the window), and an identical NON-ZERO match across two different
  kernels cannot be a kernel artifact (a zero-out kernel would read 00).
  The WRN set being identical shows the effective DT/init writes are the
  same on both kernels.
* The seven differing registers are likewise never written by the AP-side
  driver in either mode. They hold repeater-internal status/activity
  state: in the working mode the link is active at the repeater, in the
  broken mode the repeater (enabled, RPTR_OK) has never seen one.
  Register names beyond the driver's #defines are not public; the pattern
  (all-zero broken vs non-zero working) is the datum.
* The repeater platform device on this kernel: c400000.spmi:pmic@7:phy@fd00
  (compatible qcom,pm8550b-eusb2-repeater), driver qcom-eusb2-repeater
  (built-in), regulators vdd18/vdd3, DT tuning
  qcom,tune-usb2-amplitude / -disc-thres / -preem. The separately-present
  phy-qcom-m31-eusb2.ko is the SM8750 M31 HSPHY driver, not bound here.
* Residual caveat (cheap to close, optional): a normal boot of the CI
  a699dd6 kernel with the same manual read would confirm the seven
  activity registers on the identical kernel. The tuning-register verdict
  is already conclusive in both directions without it.
